# Task Spec Authoring

사용자의 대략적인 요청을 구현 착수 전에 확인할 수 있는 Task Spec으로 정리한다. 이 trigger는 명세 문서 작성을 허가하지만 코드 구현, 의존성 설치 또는 아키텍처 변경을 허가하지 않는다.

## 작업 절차

1. 루트 `AGENTS.md`, 사용자가 제공한 요청과 관련 기존 문서를 읽는다.
2. `docs/task_specs/`에서 같은 작업의 문서가 있는지 확인한다. 기존 명세 보완 요청이면 해당 문서를 수정하고, 새 작업이면 기존 최대 번호 다음의 `NNN_제목.md`를 만든다.
3. 사용자 표현을 유지하면서 모호한 내용을 실행 가능한 조건으로 정리한다. 근거 없이 기능, 기술, 의존성 또는 정책을 추가하지 않는다.
4. 구현 결과를 관찰해 통과·실패를 판정할 수 있는 acceptance criteria를 작성한다.
5. 사용자 승인이 필요한 의존성, 아키텍처, 파일 분할 또는 리팩터링은 확정 요구사항으로 만들지 말고 `작업 전 확인 사항`에 구분한다.
6. 요구사항을 작은 검증 단위로 반복 수행할 작업 루프 계획을 작성한다.
7. 자동 검증과 사용자 관점의 수동 검수를 구분해 검증 방법을 작성한다. 저장소에 존재하지 않는 명령은 실행 가능한 것으로 단정하지 않는다.
8. 승인 필요, 외부 환경 부재, 반복 실패와 범위 이탈을 포함한 중지 조건을 작성한다.
9. Acceptance Criteria 충족, 검증 근거, 범위 준수와 기록 완료를 포함한 성공 완료 조건을 작성한다.
10. 문서만 작성한 뒤 구현은 시작하지 않는다.

## 문서 구성

Task Spec에는 작업에 필요한 범위에서 다음 항목을 포함한다.

1. **Goal**: 해결할 문제와 기대 결과
2. **Background**: 현재 상태와 작업이 필요한 이유
3. **Requirements**: 구현해야 하는 기능과 동작
4. **Acceptance Criteria**: 관찰 가능하고 판정 가능한 완료 조건
5. **Out of Scope**: 이번 작업에서 명시적으로 제외할 항목
6. **Constraints**: 기술, 권한, 호환성 또는 작업 방식의 제한
7. **작업 전 확인 사항**: 사용자의 결정이나 승인이 필요한 미확정 항목
8. **작업 루프 계획**: 반복 단위, 순서, 각 반복에서 검증하고 다음 단계로 이동하는 기준
9. **검증 방법**: 자동 검증, DB·외부 연동 확인과 사용자 관점의 수동 검수 방법
10. **중지 조건**: 사용자 승인이나 외부 조건이 필요하거나 안전하게 계속할 수 없는 상황과 보고 내용
11. **완료 조건**: 전체 acceptance 통과, 검증 근거, 범위 준수와 후속 기록을 포함한 성공 종료 기준

항목 이름은 한글로 작성하되 `Goal`, `Requirements`, `Acceptance Criteria`, `Out of Scope`의 의미가 분명해야 한다. 불필요한 항목은 억지로 채우지 않는다.

## 작성 경계

- 요구사항과 제안, 확정 사항과 미확정 사항을 구분한다.
- 구현 방법보다 기대 동작과 완료 조건을 우선한다.
- 기존 문서 번호를 재사용하거나 관련 없는 Task Spec을 덮어쓰지 않는다.
- 실행하지 않은 구현이나 검증을 완료된 것으로 기록하지 않는다.
- 작업 루프는 무제한 반복으로 작성하지 않는다. 동일 원인의 반복 실패 횟수, 승인 필요, 외부 환경 부재와 범위 이탈 등 구체적인 중지 기준을 둔다.
- 완료 조건은 Acceptance Criteria 번호와 연결하고, 실행하지 못한 검증을 성공으로 간주하지 않는다.
- 완료 보고에는 작성하거나 수정한 Task Spec 경로와 작업 전 확인이 필요한 항목을 알린다.
