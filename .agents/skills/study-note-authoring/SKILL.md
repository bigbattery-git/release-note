# Study Note Authoring

현재 대화, Task Spec, Work Log, 실제 코드와 검증 결과를 근거로 사용자가 구현을 직접 유지보수하기 위해 학습할 내용을 문서화한다. 이 trigger는 학습 문서 작성을 허가하지만 코드 구현이나 의존성·아키텍처 변경을 허가하지 않는다.

## 저장 규칙

1. 문서는 `docs/study/`에 저장한다.
2. 새 문서 파일명은 `YYYYMMDD_NNN_제목.md` 형식을 사용한다.
3. `YYYYMMDD`는 작성일이고, `NNN`은 같은 날짜 문서 중 기존 최대 번호 다음의 세 자리 번호다.
4. 같은 주제의 보완 요청이면 기존 문서를 수정하고, 다른 학습 주제이면 새 번호를 사용한다.
5. 제목은 학습 대상을 드러내는 짧은 한국어로 작성하며 기술명과 코드 식별자는 원문을 유지한다.

## 작성 절차

1. 루트 `AGENTS.md`, 관련 Task Spec과 Work Log, 실제 구현 파일을 읽는다.
2. 구현된 요청 흐름과 component·server·외부 API·DB 사이의 연결을 확인한다.
3. 사용자가 수정할 가능성이 높은 지점과 장애가 발생하기 쉬운 경계를 찾는다.
4. 실제 작업 내용과 공부할 개념을 연결하되, 확인하지 않은 구현이나 검증을 완료로 쓰지 않는다.
5. 공식 문서가 필요한 최신 기술 내용은 공식 자료로 확인해 링크한다.
6. 문서만 요청된 경우 코드, 설정과 DB를 변경하지 않는다.

## 문서 구성

작업 규모에 맞춰 다음 내용을 포함한다.

1. **학습 목표**: 문서를 읽은 뒤 설명하거나 수정할 수 있어야 하는 범위
2. **구현한 작업**: 실제 변경과 선택 이유
3. **전체 동작 흐름**: UI부터 외부 API와 DB까지의 호출·데이터 흐름
4. **파일별 책임**: 유지보수 시 먼저 볼 파일과 변경 영향
5. **공부할 주제**: 우선순위, 핵심 질문, 이 구현과의 연결점
6. **유지보수 시나리오**: 기술 추가·비활성화, API 오류, schema 변경 등 실제 대응 방법
7. **검증 방법**: test, typecheck, build, migration, DB와 화면 확인
8. **주의사항**: secret, migration 재실행, transaction, Docker mount와 image rebuild
9. **학습 체크리스트**: 사용자가 스스로 설명하거나 실습해 볼 수 있는 판정 가능한 항목
10. **공식 참고 자료**: 실제 학습에 필요한 1차 자료

## 작성 원칙

- 일반 이론을 나열하지 말고 현재 저장소의 파일, 데이터와 장애 사례에 연결한다.
- 코드를 전부 복사하지 않고 책임, 입력·출력, 변경 지점과 실패 영향을 설명한다.
- 구현된 사실, 권장 학습, 아직 구현하지 않은 후속 범위를 구분한다.
- 명령은 저장소에 실제 존재하는 script를 우선하며 실행하지 않은 결과를 성공으로 적지 않는다.
- 비밀번호, token, 개인 정보와 실제 `.env` 값은 기록하지 않는다.
- 운영 DB에 직접 적용할 변경 예시는 migration으로 관리해야 함을 명시한다.
- 완료 보고에는 작성하거나 수정한 학습 문서 경로와 가장 먼저 공부할 주제를 알린다.
