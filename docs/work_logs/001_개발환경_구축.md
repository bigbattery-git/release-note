# 001. 개발 환경 구축과 Fast Refresh 문제 해결

- 작업일: 2026-09-06
- 작업 범위: Docker Compose 기반 최소 실행 환경, TypeScript 전환, Tailwind CSS 연결, Next.js 자동 갱신
- 기록 기준: 이번 대화의 작업·검증 결과와 최종 파일 구성

## 1. 작업 목적

빈 프로젝트에서 Node.js 스케줄러, Next.js, MariaDB를 함께 실행할 개발 환경을 준비했다.
호스트에서 각 서비스를 따로 실행하지 않고 `docker compose up --build`로 시작하는 것이 목표였다.
실제 API, 데이터 저장·조회, ORM, 애플리케이션 DB 스키마, 인증, 테스트 코드, CI/CD는 구현하지 않았다.

## 2. 수행한 작업과 선택 이유

### Docker Compose와 기본 실행 환경

- `scheduler`, `web`, `mariadb` 세 서비스를 구성했다.
- Node.js 앱 이미지는 `node:24-bookworm-slim`, DB는 `mariadb:11.8`을 사용했다.
- Next.js는 컨테이너 시작 시 개발 서버를 자동 실행하고, 호스트의 `127.0.0.1:3000`으로 접근하도록 했다.
- MariaDB에는 데이터 보존용 named volume과 공식 `healthcheck.sh` 기반 상태 확인을 설정했다.
- 애플리케이션 DB·테이블·초기화 SQL은 만들지 않았다. MariaDB 자체 시스템 DB 초기화는 공식 이미지에 맡겼다.
- 패키지 버전과 lockfile을 고정하고 Dockerfile에서 `npm ci`를 사용했다.

### 스케줄러

구현 전에 `node-cron`, `cron`, `node-schedule`의 동작 방식과 장단점을 비교했다.
이번 요구는 매초 로그 한 줄을 출력하는 것이므로, 간결한 cron 표현식으로 구현할 수 있는 `node-cron`을 선택했다.

`* * * * * *`로 매초 `수신중`을 출력하도록 구현하고, 종료 신호를 받으면 예약 작업을 정리하도록 했다.
애플리케이션에는 `setTimeout`, `setInterval`, 직접 작성한 Timer 반복 루프를 사용하지 않았다.
Timer 제한은 애플리케이션 코드에 적용하고 스케줄링 라이브러리 내부 구현은 허용하는 것으로 설명했다.

이후 사용자가 로그 출력을 주석 처리했다. TypeScript 전환과 후속 수정에서는 이 변경을 보존했다.
따라서 최초 로그 출력 검증 결과와 최종 코드의 로그 비활성 상태는 구분해야 한다.

### TypeScript 전환

- 스케줄러의 `index.js`를 `index.ts`로 전환했다.
- Next.js의 `layout.js`, `page.js`를 `.tsx`로 전환하고 props 타입을 추가했다.
- 각 앱에 `tsconfig.json`, TypeScript 및 필요한 타입 선언 패키지, `typecheck` 명령을 추가했다.
- 스케줄러는 Node.js 24의 내장 TypeScript 지원으로 직접 실행한다. 실행과 타입 검사는 별개이며, 타입 검사는 `tsc --noEmit`으로 수행한다.
- Dockerfile의 소스 경로와 실행 명령도 변경했다.

### Tailwind CSS 연결

Next.js에 `tailwindcss`, `@tailwindcss/postcss`, `postcss`를 개발 의존성으로 추가했다.
`postcss.config.json`에 플러그인을 등록하고 `app/globals.css`에서 Tailwind를 import했다.
루트 layout에서 CSS를 불러오고 body의 `min-h-screen` 클래스로 CSS 생성 여부를 확인했다.
별도 UI나 Tailwind 실행 프로세스는 추가하지 않았다.

## 3. 발생한 문제와 해결 과정

### 문제 A. 페이지를 수정해도 이전의 빈 화면이 표시됨

**증상:** 사용자가 `web/app/page.tsx`에 문구를 추가했지만, 실행 중인 페이지에는 기존 `null` 결과가 표시되었다.

**원인:** Dockerfile의 `COPY`는 이미지 빌드 시점의 파일만 복사한다. Next.js가 개발 모드여도 호스트에서 수정한 파일이 컨테이너로 전달되지 않으면 변경을 감지할 수 없다.

**해결:** Compose에 `./web/app:/app/app` bind mount를 추가했다. Windows Docker 환경의 변경 감지를 위해 Webpack 개발 모드와 `WATCHPACK_POLLING=1000`을 설정했다. 호스트의 `node_modules`와 `.next`는 마운트하지 않았다.

**초기 검증의 한계:** 서버를 재시작하지 않고 HTTP를 다시 요청했을 때 바뀐 HTML이 반환되는 것은 확인했다. 하지만 이 검증은 브라우저의 자동 갱신을 입증하지 못했다. 사용자가 수동 새로고침이 여전히 필요하다고 알려 주어 HMR 연결을 추가 조사했다.

### 문제 B. 새로고침하면 바뀌지만 저장만으로는 화면이 갱신되지 않음

**증상:** 파일 변경은 서버에 반영되었으나 브라우저 화면은 자동으로 바뀌지 않았다.

**조사:** 페이지와 개발용 JavaScript의 HTTP 응답을 확인하고, 브라우저를 열어둔 상태에서 소스를 임시 변경했다. 화면이 그대로인 것을 재현한 뒤 HMR WebSocket의 Origin을 바꿔 비교했다.

| 확인 항목 | 결과 |
| --- | --- |
| 변경 후 일반 페이지 HTTP 요청 | 변경된 문구 반환 |
| `Origin: http://127.0.0.1:3000`으로 HMR 연결 | `Unauthorized` |
| `Origin: http://localhost:3000`으로 HMR 연결 | `101 Switching Protocols` |

**원인:** 사용 중인 Next.js의 개발용 Origin 검사가 `127.0.0.1`의 HMR 연결을 차단했다. 서버는 `0.0.0.0`으로 실행되었고 `localhost`는 기본 허용되지만, 접속에 사용한 `127.0.0.1`은 추가 허용되어 있지 않았다. 일반 HTTP 요청과 자동 갱신 알림용 WebSocket은 서로 다른 경로이므로, 새로고침만 성공할 수 있었다.

**해결:** `web/next.config.ts`에 아래 설정을 추가하고 Dockerfile이 이 파일도 복사하도록 수정했다.

```ts
const nextConfig: NextConfig = {
  allowedDevOrigins: ['127.0.0.1'],
};
```

**재검증:** 수정한 로컬 개발 서버를 `127.0.0.1:3001`에서 실행했다. 브라우저를 새로고침하지 않은 상태에서 소스를 변경했을 때 화면이 자동으로 바뀌고, 콘솔에 `[HMR] connected`, `[Fast Refresh] rebuilding`, `[Fast Refresh] done`이 출력되는 것을 확인했다. 확인용 문구를 원본으로 복원한 뒤에도 자동 반영을 확인했다.

## 4. 검증 결과와 남은 확인

| 항목 | 확인 결과 및 범위 |
| --- | --- |
| 최초 스케줄러 로그 | 로컬 Node.js에서 5회 출력, 간격 987~1009ms |
| TypeScript 전환 | 두 앱 타입 검사 통과, 스케줄러 TS 실행 및 작업 등록 확인 |
| Next.js와 Tailwind | 페이지·CSS HTTP 200, 생성 CSS에 `min-h-screen` 포함 확인 |
| 자동 갱신 | 수정한 로컬 서버에서 실제 브라우저의 새로고침 없는 갱신 확인 |
| 의존성 | 필요한 런타임·개발 의존성 확인, 설치 당시 npm audit 취약점 0개 |
| Docker Compose·MariaDB | 에이전트 환경에서 Docker CLI를 사용할 수 없어 직접 빌드·기동 및 DB healthy 검증은 수행하지 못함 |

사용자는 앞선 변경 후 접속 및 수동 새로고침 시 반영을 확인했다. 최종 Origin 설정을 적용한 컨테이너의 자동 갱신 결과와 MariaDB 상태는 별도의 직접 검증 기록이 없다.

설정 파일은 이미지에 포함되므로 기존 컨테이너에는 한 번 재빌드가 필요하다.

```sh
docker compose up --build
```

이후 `http://127.0.0.1:3000/`을 열고 `web/app/page.tsx`를 수정·저장해 자동 반영을 확인한다. `app` 아래 소스 변경은 재빌드 없이 반영되며, 패키지·Dockerfile·`app` 밖의 설정·스케줄러 변경은 재빌드가 필요하다.

## 5. 이번 작업에서 얻은 점

- 개발 모드 실행, 컨테이너에 소스 전달, 파일 변경 감지, 브라우저 HMR 연결을 각각 확인해야 한다.
- 새 HTTP 요청에 변경된 HTML이 나온다는 사실만으로 Fast Refresh가 동작한다고 판단하면 안 된다.
- 자동 갱신은 브라우저를 열어둔 상태에서 저장하고 실제 화면 변화를 확인해야 한다.
- 같은 로컬 서버라도 `localhost`와 `127.0.0.1`은 개발용 Origin 검사에서 다르게 처리될 수 있다.
- 로컬 검증, 사용자 확인, 컨테이너 직접 검증을 기록에서 구분해야 한다.

## 6. 주요 변경 파일

- `compose.yaml`: 서비스 구성, 포트, DB 볼륨·상태 확인, 웹 소스 마운트와 폴링
- `scheduler/index.ts`, `scheduler/tsconfig.json`, `scheduler/Dockerfile`: 스케줄링 및 TypeScript 실행 환경
- `web/app/layout.tsx`, `web/app/page.tsx`, `web/app/globals.css`: TypeScript 페이지와 Tailwind 연결
- `web/postcss.config.json`, `web/tsconfig.json`, `web/next.config.ts`, `web/Dockerfile`: CSS 처리, 타입 검사, HMR Origin 허용, 컨테이너 실행
- 각 앱의 `package.json`, `package-lock.json`: 의존성과 실행·검사 명령
- `README.md`, `.gitignore`, 각 앱의 `.dockerignore`: 실행 안내와 생성물 제외
