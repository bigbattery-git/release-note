# Work Log 작성 규칙

## 목적과 작성 시점

하나의 작업을 마무리한 뒤 무엇을 했고, 어떤 문제가 발생했으며, 어떻게 해결했는지 기록한다.
작업 로그는 Task Spec과 별개인 수행 기록이다. 요구사항을 그대로 복사하기보다 실제 변경과 판단 근거를 남긴다.
문서 작성만을 위해 완료되지 않은 작업이나 확인하지 않은 결과를 완료로 표현하지 않는다.

## 저장 위치와 파일명

- 위치: `docs/work_logs/`
- 형식: `NNN_제목.md`
- 번호: `001`, `002`, `003` 순서로 기존 최대 번호 다음 값을 사용한다.
- 제목: 작업의 핵심 내용을 짧은 한국어로 작성하고, 단어 사이는 밑줄로 구분한다.
- 예시: `001_개발환경_구축.md`, `002_뉴스_수집_구현.md`
- 기존 로그를 덮어쓰거나 번호를 재사용하지 않는다. 같은 작업의 기록 보완은 해당 문서를 수정하고, 별도 후속 작업은 새 번호로 작성한다.

## 기본 구성

문서 제목은 `# NNN. 작업 제목`으로 작성한다. 제목 아래에 작업일, 작업 범위, 기록 기준을 적는다.
작업일은 `YYYY-MM-DD` 형식으로 쓰고, 여러 날에 걸쳤다면 기간을 적는다.

| 순서 | 항목 | 작성 내용 |
| --- | --- | --- |
| 1 | 작업 목적 | 왜 작업했는지, 해결하려던 문제와 범위 |
| 2 | 수행한 작업과 선택 이유 | 실제 변경 사항, 주요 선택과 그 이유 |
| 3 | 발생한 문제와 해결 과정 | 증상, 조사·근거, 원인, 해결, 재검증 |
| 4 | 검증 결과와 남은 확인 | 검증 방법·환경·결과, 미검증 항목과 후속 조치 |
| 5 | 이번 작업에서 얻은 점 | 다음 작업에 적용할 구체적인 교훈 |
| 6 | 주요 변경 파일 | 관련 파일 경로와 변경 목적 |
| 7 | 참고 자료 | 실제 참고한 문서나 근거 링크 |

작업 규모에 맞춰 분량을 조절한다. 문제가 없었다면 이를 짧게 적고, 교훈이나 참고 자료가 없다면 해당 항목은 생략한다.
형식을 채우기 위해 문제, 대안, 교훈을 만들어내지 않는다.

## 작성 원칙

### 변경 내용과 판단 근거

- 도구 호출 순서나 대화 전체를 나열하지 않는다. 결과를 이해하는 데 필요한 과정만 정리한다.
- 무엇을 바꿨는지와 왜 바꿨는지를 함께 설명한다.
- 대안을 실제 비교했다면 선택 이유를 남긴다. 검토하지 않은 대안을 검토했다고 쓰지 않는다.
- 실패한 접근이나 초기 판단 오류도 최종 해결에 중요한 경우 기록한다.
- 기존 사용자 변경을 보존했거나 작업 중 범위가 달라졌다면 결과에 영향을 주는 내용만 명시한다.

### 문제 해결 기록

문제별로 다음 흐름을 사용한다.

1. **증상:** 어떤 상황에서 무엇이 기대와 달랐는가?
2. **조사와 근거:** 어떤 로그, 응답, 코드, 재현 결과를 확인했는가?
3. **원인:** 확인된 원인은 무엇인가? 추정이라면 추정임을 표시한다.
4. **해결:** 무엇을 변경했고, 그 변경이 원인을 어떻게 해결하는가?
5. **재검증:** 수정 후 원래 증상이 사라졌는지 어떻게 확인했는가?

### 검증 결과의 정확성

- 에이전트의 직접 검증, 사용자의 확인, 아직 확인하지 못한 항목을 구분한다.
- 로컬 실행, Docker 컨테이너 실행 등 검증 환경을 명시한다.
- 타입 검사나 HTTP 응답 성공을 전체 기능 검증으로 확대해서 표현하지 않는다.
- 예를 들어 Fast Refresh는 HTTP 재요청 성공뿐 아니라 새로고침 없는 브라우저 갱신을 확인해야 한다.
- 과거에 확인한 동작이 최종 코드에서 비활성화되었다면 시점과 최종 상태를 구분한다.
- 미검증 항목에는 이유와 필요한 다음 확인을 적는다. 당시 결과를 영구적인 보장처럼 쓰지 않는다.
- 실행하지 않은 테스트, 빌드, 명령을 성공했다고 기록하지 않는다.

### 가독성과 정보 관리

- 한국어로 작성하고 파일명, 명령어, 기술 식별자는 원문을 사용한다.
- 파일 경로는 저장소 루트 기준으로 적는다.
- 비교와 검증 결과는 표를, 실행 명령과 핵심 설정은 짧은 코드 블록을 활용한다.
- 전체 소스, 긴 로그, 중복된 실행 안내는 붙여넣지 않는다.
- 비밀번호, 토큰, 개인 정보 등 민감한 값은 기록하지 않는다.
- 참고 링크는 실제 사용한 자료만 남긴다.

## 작성 템플릿

아래 템플릿을 복사한 뒤 작업에 맞게 작성한다. 대괄호 안내 문구는 실제 내용으로 바꾸거나 삭제한다.

```markdown
# NNN. 작업 제목

- 작업일: YYYY-MM-DD
- 작업 범위: [실제로 수행한 범위]
- 기록 기준: [작업 대화, 변경 파일, 실행 결과 등]

## 1. 작업 목적

[배경과 목표]

## 2. 수행한 작업과 선택 이유

[주요 변경과 판단 근거]

## 3. 발생한 문제와 해결 과정

### 문제 A. [증상을 나타내는 제목]

**증상:** [기대와 실제 동작]

**조사와 근거:** [확인한 사실]

**원인:** [확정 원인 또는 추정과 한계]

**해결:** [변경 사항]

**재검증:** [원래 증상 해소 여부]

## 4. 검증 결과와 남은 확인

| 항목 | 방법·환경 | 결과 및 한계 |
| --- | --- | --- |
| [확인 항목] | [직접 검증 / 사용자 확인 등] | [결과] |

[미검증 이유와 필요한 후속 조치]

## 5. 이번 작업에서 얻은 점

[다음 작업에 적용할 구체적인 교훈]

## 6. 주요 변경 파일

- `경로`: [변경 목적]

## 7. 참고 자료

- [자료 제목](URL)
```

## 작성 후 확인

- 번호와 제목이 기존 로그와 충돌하지 않는가?
- 실제 변경, 발생한 문제, 해결 근거가 기록되었는가?
- 검증 환경과 결과, 미확인 사항이 구분되어 있는가?
- 최종 코드와 기록이 일치하고, 임시 검증 변경을 최종 기능으로 적지 않았는가?
- 불필요한 내용이나 민감한 정보가 포함되지 않았는가?
