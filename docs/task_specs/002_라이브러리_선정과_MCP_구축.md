# 002. 라이브러리 선정과 MCP 구축

- 작성일: 2026-09-10
- 기준: 라이브러리 조사와 MCP 구축을 위한 사전 Task Spec
- 상태: 구현 및 Acceptance Criteria 검증 완료

## 1. 목표

MariaDB를 사용하는 애플리케이션의 데이터 접근, 캐싱, 세션, 비밀번호 처리,
입력 검증과 Form 처리를 위한 라이브러리를 조사하고 선정한다. 승인된 라이브러리를
설치하고, Zod와 React Hook Form을 제외한 항목은 실제 기능 구현 전의 초기 설정까지 마친다.

GitHub Release 수집 구현에 필요한 저장소 내 기술 문서를 read-only MCP resource로 제공한다.
연결된 coding client가 사용자의 기능 추가 요청을 처리할 때 해당 문서를 발견하고 읽어
API 계약과 구현 기준으로 활용할 수 있게 한다.

## 2. 배경

- 현재 저장소에는 Docker Compose 기반 `scheduler`, `web`, `mariadb` 실행 환경이 있다.
- `web`에는 Next.js, React, Tailwind CSS와 개발 필수 패키지만 설치되어 있다.
- 기존 Task Spec에서는 ORM, DB schema, 인증과 실제 업무 기능을 제외했으므로 이번 작업은 별도 후속 범위로 관리한다.
- 후보로 언급된 기술은 MariaDB 연동 패키지, query builder 또는 ORM, TanStack Query,
  `iron-session`, `bcrypt`, Zod, React Hook Form이다.
- GitHub Release 수집을 위한 기준 문서로 `docs/technology_update_api_research.md`가 존재한다.
- MCP는 GitHub에서 Release를 직접 수집하거나 코드를 대신 작성하는 서비스가 아니다.
  저장소의 기준 문서를 MCP resource로 제공하고, 실제 구현은 이 resource를 읽은 coding client가 수행한다.
- 각 기술은 담당하는 계층이 다르다. 특히 TanStack Query의 client-side server state cache와
  Next.js의 server-side cache는 구분해서 적용 범위를 결정해야 한다.

## 3. 요구사항

### 3.1 라이브러리 조사와 선정

- 다음 영역별로 현재 기술 구성과 호환되는 후보를 조사한다.
  - MariaDB 연결에 필요한 driver 또는 adapter
  - type-safe query builder 또는 ORM
  - client-side server state 조회와 cache 및 TanStack Query Devtools
  - SSR 환경에서 사용할 session 관리
  - 비밀번호 hash와 검증
  - server/client 공통 입력 schema 검증
  - React Form 상태와 validation 연동
- 선택지가 실질적으로 존재하는 영역은 후보를 2~3개로 제한해 비교한다.
- 후보별로 다음 내용을 확인한다.
  - Next.js 16, React 19, Node.js 24, MariaDB 11.8과의 호환성
  - SSR, React Server Components 및 Docker 환경에서의 제약
  - 유지보수 상태와 공식 문서 제공 여부
  - 추가 runtime dependency와 native build 필요 여부
  - 적용 범위와 중복 역할
- 조사 결과에는 영역별 권장안, 대안, 선택 이유와 저장소에 미치는 영향을 포함한다.
- package 이름과 version은 조사 결과를 사용자에게 제안하고 승인받은 후 확정한다.

승인된 조합은 다음과 같다.

| 영역 | package 및 version |
| --- | --- |
| MariaDB와 query builder | `kysely@0.29.5`, `mysql2@3.24.4` |
| client-side server state | `@tanstack/react-query@5.102.8` |
| Query debugging | `@tanstack/react-query-devtools@5.102.8` |
| session | `iron-session@9.0.1` |
| password hashing | `bcrypt@6.0.0`, `@types/bcrypt@6.0.0` |
| schema와 Form | `zod@4.5.4`, `react-hook-form@7.87.0` |
| MCP | `@modelcontextprotocol/server@2.0.0`, 검증용 `@modelcontextprotocol/client@2.0.0` |

### 3.2 의존성 설치와 최소 설정

- 사용자에게 승인받은 package만 필요한 workspace에 설치한다.
- production runtime에 필요한 package와 개발 전용 package를 구분한다.
- lockfile을 함께 갱신하고 Docker의 `npm ci` 흐름을 유지한다.
- 환경 변수 이름과 필수 설정을 문서화하되 비밀번호, session secret과 같은 실제 secret은 저장소에 기록하지 않는다.
- 라이브러리가 설치되었다는 이유만으로 사용하지 않는 wrapper, provider, directory 또는 추상화를 미리 만들지 않는다.

### 3.3 초기 설정 범위

- MariaDB driver 또는 adapter는 환경 변수 기반 connection 설정과 connection pool을 준비한다.
- 선정한 query builder 또는 ORM은 MariaDB connection을 재사용할 수 있는 client 설정까지 준비한다.
- DB schema, model과 migration은 만들지 않고 실제 연결을 확인할 수 있는 최소 검증 경로만 둔다.
- TanStack Query는 App Router에서 사용할 `QueryClient`와 client-side provider를 구성하고 root layout에 연결한다.
- 개발 환경에서만 사용할 수 있도록 TanStack Query Devtools를 provider에 연결한다.
- SSR에서 TanStack Query hydration이 즉시 필요하지 않으면 관련 경계를 미리 만들지 않는다.
- `iron-session`은 환경 변수에서 secret을 읽는 session option과 cookie 설정을 준비한다.
- session cookie는 개발·production 환경에 따라 `secure` 옵션이 올바르게 적용되도록 한다.
- password hashing package는 server에서만 사용할 hash·verify 초기 모듈을 준비하고 client bundle에 포함되지 않게 한다.
- Zod와 React Hook Form은 승인된 package 설치까지만 수행한다. 공통 schema, resolver, Form component와 provider는 만들지 않는다.
- Zod와 React Hook Form을 연결하는 별도 resolver package가 필요하면 자동으로 추가하지 않고 먼저 제안한다.

### 3.4 역할별 적용 원칙

- MariaDB 연결 계층과 query builder/ORM의 책임을 구분하고, 동일 역할의 package를 중복 설치하지 않는다.
- TanStack Query는 browser에서 관리할 server state가 확인된 경우에만 적용한다.
- Next.js SSR 결과의 cache 또는 server-side data cache가 필요하면 TanStack Query와 별도의 문제로 조사한다.
- session에는 인증 상태를 식별하는 데 필요한 최소 정보만 저장한다.
- 비밀번호 원문은 저장하거나 log에 출력하지 않고, 승인된 password hashing library로 hash와 검증을 수행할 수 있게 한다.
- Zod schema를 server-side 신뢰 경계의 검증 기준으로 사용하고, React Hook Form과 연결할 때 같은 규칙을 재사용할 수 있게 한다.

### 3.5 GitHub Release 문서 MCP 구축

- `docs/technology_update_api_research.md`를 MCP의 기준 source로 사용한다.
- MCP client가 문서를 발견할 수 있도록 안정적인 resource URI, 이름, 설명과 MIME type을 정의한다.
- MCP client가 resource 목록을 조회하고 문서 전문을 읽을 수 있게 한다.
- coding client가 자연어 기능 요청 중 문서를 능동적으로 선택할 수 있도록 같은 내용을 반환하는 read-only tool을 함께 제공한다.
- resource 내용은 source Markdown과 불일치하는 별도 사본을 만들지 않고 실행 시 source 파일에서 읽는다.
- MCP는 문서를 read-only로 제공하며 source 문서 수정, 임의 코드 생성 또는 GitHub API 호출 권한을 갖지 않는다.
- resource 설명에는 GitHub Release 수집 기능을 구현할 때 참고하는 문서임을 명확히 표시한다.
- source 파일이 없거나 읽을 수 없을 때 protocol에 맞는 오류를 반환하고 process 전체가 비정상 종료되지 않게 한다.
- MCP SDK와 관련 package는 공식 문서와 현재 Node.js 환경의 호환성을 확인한 뒤 승인받아 설치한다.
- 초기 transport는 coding client에서 로컬로 연결할 수 있는 방식을 조사해 제안하고 승인 후 확정한다.
- 단순 process 기동 확인이 아니라 MCP client를 사용한 `initialize`, `resources/list`, `resources/read`까지 검증할 수 있게 구성한다.

## 4. 완료 조건

다음 조건을 모두 만족해야 한다. 이 표는 요구사항이며 실제 검증 결과는 Work Log에 기록한다.

| 번호 | Acceptance Criteria |
| --- | --- |
| 1 | 각 라이브러리 영역에서 필요한 후보를 최대 2~3개로 비교하고, 권장안·대안·선택 이유와 영향 범위를 사용자에게 제시해 승인을 받는다. |
| 2 | 승인된 package만 필요한 workspace에 설치되고 해당 `package-lock.json`이 함께 갱신된다. |
| 3 | 선정한 MariaDB driver 또는 adapter와 query builder/ORM client를 통해 실행 중인 MariaDB에 실제로 연결할 수 있다. |
| 4 | TanStack Query provider가 App Router의 root layout에 연결되고 애플리케이션이 provider 내부에서 정상적으로 render된다. |
| 5 | TanStack Query Devtools는 개발 환경에서 사용할 수 있고 production 환경에서는 활성화되지 않는다. |
| 6 | `iron-session` config가 환경 변수 기반 secret과 환경별 cookie 설정을 사용하며 실제 secret을 저장소에 포함하지 않는다. |
| 7 | password hash·verify 초기 모듈이 server에서 동작하고 비밀번호 원문을 log 또는 client bundle에 노출하지 않는다. |
| 8 | Zod와 React Hook Form은 승인된 package 설치까지만 수행하며 schema, Form component, provider와 validation resolver를 생성하지 않는다. |
| 9 | MCP client에서 `initialize`, `resources/list`, `resources/read`가 성공한다. |
| 10 | MCP의 resource metadata만으로 GitHub Release 수집 구현용 문서임을 식별할 수 있다. |
| 11 | MCP가 반환한 문서 내용이 `docs/technology_update_api_research.md`와 일치한다. |
| 12 | 기준 문서가 없거나 읽을 수 없을 때 MCP가 protocol에 맞는 오류를 반환하고 비정상 종료되지 않는다. |
| 13 | 변경된 각 workspace에서 깨끗한 의존성 설치와 TypeScript typecheck가 성공한다. |
| 14 | 회원가입·로그인 기능, 실제 서비스 DB schema, migration과 Release 수집 기능이 추가되지 않는다. |

## 5. 작업 범위에서 제외하는 항목

- 회원가입·로그인 UI와 전체 인증 flow 구현
- 사용자, session, Repository, Release 등 실제 서비스 DB schema와 migration 작성
- 실제 비즈니스 데이터의 저장·조회 기능
- 구체적인 조회 대상이 정해지지 않은 TanStack Query query, prefetch와 hydration 구현
- Next.js 전체 cache 정책 설계
- Zod schema, React Hook Form component와 validation resolver 구성
- MCP가 직접 GitHub Release를 조회하거나 애플리케이션 코드를 생성·변경하는 기능
- MCP를 통한 MariaDB 조회와 변경
- 배포용 secret 발급과 production 배포
- 요청하지 않은 UI 디자인 또는 화면 구현

## 6. 제약사항

- 문서와 기록은 한국어로 작성하고 기술명, package명, 코드 식별자와 명령어는 원문을 유지한다.
- 새 라이브러리 설치와 관련 파일 변경은 사용자에게 이유, 대안과 영향을 설명하고 승인받은 뒤 수행한다.
- 아키텍처 변경, 파일 분할 또는 리팩터링이 필요하면 별도 승인을 받는다.
- 조사 결과만으로 설치, 구현 또는 검증이 끝난 것으로 기록하지 않는다.
- 기존 `scheduler`, `web`, `mariadb` 실행 환경과 Docker 기반 개발 흐름을 깨뜨리지 않는다.

## 7. 작업 전 확인 사항

1. 승인된 설정은 session cookie 이름 `news-summary-session`, `SESSION_PASSWORD` 환경 변수,
   `iron-session` 기본 TTL, production에서만 활성화하는 `secure` cookie이다.
2. password hashing은 비동기 `bcrypt`와 work factor `12`를 사용하고 UTF-8 기준 72 bytes를 초과하는 입력을 거부한다.
3. MCP는 로컬 coding client용 stdio transport를 사용한다.
4. 구현 중 승인 범위 밖의 새 라이브러리, 아키텍처 변경, 파일 분할 또는 리팩터링이 필요하면 해당 변경 전에 사용자 승인을 받아야 한다.

## 8. 작업 루프 조건

### 8.1 루프 시작 조건

- 매 반복 시작 시 이 Task Spec과 현재 변경 상태를 다시 확인한다.
- 완료 조건에서 아직 충족되지 않은 항목 중 선행 조건이 갖춰진 하나의 작업 단위를 선택한다.
- 라이브러리 설치, 아키텍처 변경, 파일 분할 또는 리팩터링이 필요한 단계는 사용자 승인을 받은 뒤에만 시작한다.

### 8.2 반복 순서

1. 현재 반복에서 충족할 Acceptance Criteria와 변경 범위를 명시한다.
2. 범위에 필요한 조사 또는 구현만 수행한다.
3. 해당 Acceptance Criteria를 직접 판정할 수 있는 검증을 실행한다.
4. 실패하면 원인과 근거를 확인하고, 같은 범위 안에서 수정 가능한 경우 수정한 뒤 다시 검증한다.
5. 통과한 항목과 아직 충족되지 않은 항목을 구분하고 다음 작업 단위로 이동한다.
6. 모든 항목을 충족하면 최종 검증 결과와 실제 작업 내용을 Work Log에 기록하고 루프를 종료한다.

### 8.3 계속 조건

다음 조건을 모두 만족하는 동안 루프를 계속한다.

- 충족되지 않은 Acceptance Criteria가 남아 있다.
- 다음 작업이 이 Task Spec의 요구사항과 범위 안에 있다.
- 필요한 사용자 승인이 완료되어 있다.
- 검증 실패의 원인에 대해 안전하고 구체적인 다음 수정 방법이 있다.

### 8.4 성공 종료 조건

- Acceptance Criteria 1~14가 모두 충족되고 검증 근거가 있다.
- 작업 범위에서 제외한 기능이 추가되지 않았다.
- 임시 검증 코드, 실제 secret과 불필요한 의존성이 남아 있지 않다.
- 구현 결과, 문제와 해결 과정, 검증 결과 및 미확인 사항이 Work Log에 기록되어 있다.

### 8.5 중단 및 사용자 확인 조건

다음 중 하나에 해당하면 임의로 범위를 넓히지 않고 루프를 중단해 사용자에게 보고한다.

- 새 라이브러리 설치 또는 교체에 대한 승인이 필요하다.
- 아키텍처 변경, 파일 분할 또는 리팩터링 승인이 필요하다.
- session 정책, package 선택, transport 또는 보안 설정에 사용자 결정이 필요하다.
- 실제 secret, 외부 서비스 권한 또는 사용자 환경의 실행이 없으면 다음 검증을 진행할 수 없다.
- 동일한 원인의 검증 실패가 수정 후 3회 연속 반복된다.
- 다음 수정이 Task Spec의 요구사항 또는 Out of Scope를 벗어난다.

중단 시에는 충족한 조건, 실패한 조건, 확인한 원인, 시도한 수정과 사용자에게 필요한 결정을 함께 보고한다.
